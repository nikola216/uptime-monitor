# uptime-monitor

Внешняя проверка доступности сервисов на VPS. Сообщения приходят в Telegram-чат
заявок СЪЕДОБНО.

Проверка стоит снаружи, потому что изнутри сервера сбой сети не виден: там всё
отвечает, даже когда пользователи и Telegram до сервера не достают.

## Что проверяется

| Что | Как |
|---|---|
| Тренажёр английского | `GET https://trainer.voxismed.com/api/v1/health` |
| Приём заявок СЪЕДОБНО | `GET https://voxismed.com/api/health` |
| Бот тренажёра | поле `telegram` в ответе health: приложение само сообщает, жив ли его опрос Telegram |

Бот работает через long polling, а не через вебхук, поэтому спрашивать Telegram
`getWebhookInfo` бессмысленно — вебхука нет, и такая проверка всегда показывала бы
«всё хорошо». Приложение вместо этого отдаёт время последнего успешного запроса
к Telegram, и по нему видно реальное состояние канала.

## Когда приходит сообщение

- Сайт считается упавшим в этом запуске, если три попытки подряд не вернули 200.
- `#мониторинг #алерт` уходит сразу после такого запуска.
- `#мониторинг #восстановлено` приходит один раз, когда сервис снова отвечает,
  с длительностью простоя.
- Пока состояние не меняется, сообщений нет.

## ⚠️ Про частоту запусков

В расписании стоит `*/5`, но **GitHub это расписание не соблюдает**. По факту
запуски происходят раз в 2–5 часов: за первые трое суток был 21 запуск вместо
примерно 860. GitHub сильно throttlит частые cron в Actions, и повлиять на это
из репозитория нельзя.

Отсюда два следствия:

1. Порог алерта — **один** проваленный запуск, а не два. Ждать второго нет
   смысла: он может случиться через несколько часов.
2. Этот мониторинг — **редкий контрольный замер, а не сторож**. Он поймает
   долгое падение, но короткое пропустит. Для настоящей частоты нужен внешний
   сервис проверок или постоянно работающая машина вне этого VPS.

## Секреты

Settings → Secrets and variables → Actions:

- `ALERT_BOT_TOKEN` — токен бота заявок, через которого уходят сообщения;
- `ALERT_CHAT_ID` — чат, куда их слать.

## Проверить вручную

Actions → uptime → Run workflow → отметить «Отправить тестовое сообщение».
В чат придёт `#мониторинг #тест` с текущим состоянием всех проверок.

Локально без отправки:

```bash
DRY_RUN=1 STATE_FILE=/tmp/state.json python3 monitor.py
```

## Ограничения

- В публичном репозитории GitHub отключает расписание после 60 дней без
  активности. Workflow сам коммитит `.keepalive` раз в 20 дней.
- Состояние между запусками хранится в `state.json`, история его коммитов —
  это и есть журнал инцидентов.
- Репозиторий публичный, потому что для публичных репо Actions бесплатны без
  лимита минут. Секретов в коде нет, только в зашифрованных Secrets.
